Tutuca

A small framework for web apps in the browser.

Small enough to read in full, for people and for coding agents.

Open the playground Storybook Examples Demos GitHub

Tutuca covers components, typed state, rendering and event handling, and the tools to check them: tests that run without a browser, property-based tests generated from your field types, a storybook with stress tests, and a linter. State changes can be saved or shared with other tabs and devices through sync engines you plug in.

The core is about 2,000 lines of JavaScript with no npm dependencies (it includes a copy of immer). A formal model of its semantics is being written in PLT Redex.

📦

Install

npm install tutuca@next

Or import it from a CDN, no build step:

import { component, h, Host } from "https://cdn.jsdelivr.net/npm/tutuca@next/dist/tutuca.min.js";

A first component

A component is a name, typed fields, a view and the messages it handles. Click the buttons, or change the code on the left and press Ctrl+Enter. Steps replays the story's sequences, Stress test throws random messages at it and Dev shows its state, specs and lint. 

const host = new Host({ document, rootNode: document.getElementById("app") });
host.scope.register({ Counter });
host.start(host.scope.components.Counter());

That is all it takes to run it in your own page.

Build

  • 🧱
    Components with typed state

    Fields are schemas: strings, numbers, enums, options, arrays, maps, records, unions and nested components.

  • 🌳
    Views as data

    h, each, render, $if and scope build a tree the framework can inspect, lint and optimize.

  • ✉️
    Messages, not callbacks

    Events send typed messages along explicit paths to the component that handles them.

  • 🧊
    Immutable updates

    Handlers edit a draft and the result is a new state. Old states stay unchanged, which the storybook's timeline and the sync diff rely on.

  • ⚡
    A small, fast vdom

    Keyed reconciliation, with constant subtrees hoisted out of re-renders.

  • 🪟
    Embeddable

    A <tutuca-app> custom element runs apps isolated in a shadow root.

Keep and share state

  • 🔎
    A diff guided by your schemas

    After each message, tutuca can list what changed as small operations: set a field, insert into a list, edit part of a text. It uses your field types to do this, so typed text becomes text edits and a list item added at the top is one insert.

  • 🔌
    Pluggable sync

    A sync engine receives each change and can apply changes made elsewhere. Your handlers don't change. Each field says whether it is shared, kept on this device only, or not kept at all.

  • 🗂️
    Three engines included

    One saves to the browser's storage. One sends changes to a server that orders them. One keeps state in an Automerge document, so edits made at the same time merge.

  • 🧪
    Repeatable handlers

    Handlers get the time, random numbers and new ids from ctx, so tests can replay them and peers don't make clashing ids.

Try it: open the notes demo with each engine, in two tabs, and edit in one of them.

  • This browser: kept in localStorage
  • Worker: a pretend server in a shared worker, kept in IndexedDB
  • Automerge: tabs sync over a BroadcastChannel, with no server

Every demo below takes the same ?sync= option. How it works, and what an app needs to do: docs/sync.md.

Test

  • 🤖
    Headless testing

    A driver runs messages through the real task loop with or without a DOM, and reports failed tasks and invalid state.

  • 🎲
    Property-based tests from your schemas

    Random states, messages and DOM events are generated from the field and message types you already wrote.

  • 📚
    Storybook built in

    Stories with step sequences, a timeline to step back and forth, and stress tests that find and replay counterexamples.

  • 🧹
    Lint and invariants

    Catch unknown fields, views, components and handlers, and mistyped message arguments, before running. In dev, state and invariants are checked after every update.

Understand

  • 📐
    A formal specification

    A PLT Redex model of views, rendering, reconciliation, paths and the task queue, typeset as a PDF. in progress

  • 🔍
    DevTools formatters

    Components, paths and tasks show up readable in the browser console.

  • 🪶
    Fits in your head

    About 2,000 lines of core, 19 KB minified and gzipped, no npm dependencies.

  • 🧠
    Readable by coding agents

    The whole framework fits in an agent's context, so it can read it before writing code.

Learn by example

Each example builds on the one before. All of them are editable; the playground has these and every component library.

Lists and forms

Arrays of records, each to loop over them, inputs that send their value with targetValue(), and getters the view reads like fields.

Components inside components

A cart renders a line component per item. Lines handle their own messages and notify their parent of what only the parent can do. Messages declare typed arguments, checked in dev and used to generate stress tests.

Talking to the outside world

Components don't call fetch: they ask a named handler and get the answer back as a message. Stories swap the handlers, and steps can send the reply themselves.

When things go wrong

A component with three bugs. Views are data, so the linter finds them before anything runs: the Dev tab lists them. Fix them and run it again.

Demos

Small apps built from the component libraries. Most have stories in the storybook. Each one can run without sync or with any of the three engines.
