Tutuca

A small JavaScript framework for interactive web apps.

Typed state, built-in testing tools, and pluggable sync. Small enough to read in full.

Open the playground Storybook Examples Demos GitHub

Define your components, their state, and the messages they handle. Tutuca uses those definitions to render your UI, check for mistakes, and generate test cases. Explore components in the built-in storybook, then add a sync engine to save state or share changes across tabs and devices.

Start in the playground or import Tutuca into your own page. No build step required.

📦

Get started

npm install tutuca@next

Or import directly from a CDN:

import { component, h, Host } from "https://cdn.jsdelivr.net/npm/tutuca@next/dist/tutuca.min.js";

A first component

This counter introduces the four parts of a component: a name, typed fields, a view, and message handlers. Try the buttons, then edit the code and press Ctrl+Enter to run your changes.

Open Steps to replay a test sequence, Stress test to try random messages, or Dev to inspect the state, component definitions, and lint results. 

const host = new Host({ document, rootNode: document.getElementById("app") });
host.scope.register({ Counter });
host.start(host.scope.components.Counter());

To mount the counter on your own page, register it with a host and start it in an element with id app.

Build with components and messages

  • 🧱
    Components with typed state

    Describe your state with schemas for strings, numbers, enums, optional values, arrays, maps, records, unions, and nested components.

  • 🌳
    Views as data

    h, each, render, $if and scope build a tree the framework can inspect, lint and optimize.

  • ✉️
    Explicit message routing

    Events send typed messages along explicit paths to the component that handles them.

  • 🧊
    Immutable updates

    Write updates by editing a draft. Tutuca creates a new state and preserves the previous one for the storybook timeline and sync comparisons.

  • ⚡
    Efficient rendering

    A small virtual DOM matches elements by key and reuses static parts of the view.

  • 🪟
    Embeddable

    Embed an app with the <tutuca-app> custom element, which isolates its DOM and styles in a shadow root.

Save and share state

  • 🔎
    A diff guided by your schemas

    Tutuca uses your field types to describe changes as small operations: set a field, insert a list item, or edit part of a string. Adding an item at the start of a list produces one insert operation.

  • 🔌
    Pluggable sync

    Connect an engine to save changes and apply updates from elsewhere. Keep the same message handlers, and choose which fields are shared, saved only on this device, or kept only for the current session.

  • 🗂️
    Three engines included

    Use browser storage for persistence, a remote engine to exchange changes through a server, or Automerge to merge concurrent edits.

  • 🧪
    Repeatable handlers

    Read time, random numbers, and IDs through ctx. Tests can control these values to replay a run; apps use UUIDs to avoid ID collisions between peers.

  • ♻️
    Hot code reloading

    Edit a component and keep its state. Tutuca rebuilds the state with the new code: new fields take their defaults, and values that no longer fit are reset and reported along with broken invariants. Try it in the playground.

Try the notes demo: reload it to check persistence, or open the Worker or Automerge version in two tabs to see changes sync, or the Automerge relay version in two browsers. For Automerge, copy the full URL after the demo loads so both open the same document.

  • Browser storage: saves state in localStorage across reloads
  • Worker: simulates a server with a SharedWorker and saves state in IndexedDB
  • Automerge: tabs sync over a BroadcastChannel, with no server
  • Automerge relay: browsers and devices sync through the public Automerge relay; anyone with the URL can see the document

All demos support these ?sync= options. Read the sync guide for setup, field settings, and how each engine handles concurrent edits.

Test as you build

  • 🤖
    Headless testing

    A driver runs messages through the real task loop with or without a DOM, and reports failed tasks and invalid state.

  • 🎲
    Property-based tests from your schemas

    Generate random states, messages, and DOM events from your field and message types to exercise cases you might not think to write by hand.

  • 📚
    Storybook built in

    Write stories with test sequences, step through state changes on a timeline, and replay failing cases found by stress tests.

  • 🧹
    Lint and invariants

    Find unknown fields, views, components, and handlers before running your app. In development mode, Tutuca also checks message arguments, state, and invariants as your app runs.

Understand how it works

  • 📐
    A formal specification

    A PLT Redex model of views, rendering, reconciliation, paths and the task queue, typeset as a PDF. in progress

  • 🔍
    DevTools formatters

    Inspect components, paths, and tasks with readable formatting in the browser console.

  • 🪶
    A core you can read

    About 2,000 lines of JavaScript in the core, with no npm dependencies. Includes a bundled copy of Immer.

  • 🧠
    Readable by coding agents

    A compact codebase lets coding agents inspect the implementation while working on your app.

Learn by example

Edit and run each example as you go, from lists and forms to nested components and async requests. Explore more in the playground, including the component libraries.

Lists and forms

Build a todo list from an array of records. Render items with each, read input values with targetValue(), and use getters for derived values in the view.

Components inside components

Build a cart with a component for each item. Each item handles its own messages and uses notify to request changes from the cart. Typed message arguments enable runtime checks in development and generated stress tests.

Talking to the outside world

Use ask to delegate a request to a named handler and receive the result as a message. Stories can substitute test handlers or send replies directly, so you can test loading, success, and failure states.
