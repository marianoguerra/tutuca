## Runtime changes made while porting

1. **Fix: `Lens::then_items` named its collection by the inner name only.** Two collections reached through different lenses (`rows.at(0).then_items(cells)` and `rows.at(1).then_items(cells)`) got the same frame name. So their items had the same paths (`.cells[0]`), the same handler ids and the same render-cache keys. An event on one site could go to the other site's item. The name now includes the outer lens and its slot (`rows[0].cells`), as `Lens::then` already did. Regression test: `collections reached through different lenses keep their paths and handlers apart` (in `jsport_paths_collection_sources_wbtest.mbt`).
2. **Fix: events during a render ran their tasks inside the render.** `handle_tasks` clears `handling` before rendering. So an event dispatched while the view was evaluated or the DOM morphed ran its task at once, which changed the root mid-render and re-entered `render`. Such an event can be a blur when the morph removes a focused node. The host now has a `rendering` flag: `handle_tasks` returns while it is set, and `render` schedules a tick afterwards if tasks are queued. This mirrors JS's "events during rendering wait for the next tick". It also holds when the render fails (`RenderFailed`). Tests: `events during rendering wait for the next tick[ even when rendering throws]`.
3. **Missing feature, implemented: nested collections as a render source.** JS can render components from `each(field("rows"), each(field("cells"), renderIt()))`, and from `renderEach(seqItem("groups", "selected"))`. MoonBit had no way to do either from one view: `Items` can't be built outside the package, and `render_key` takes a fixed `Items`. The new `Items::then(outer, inner)` gives the items of every outer item, keyed by `(outer key, inner key)`. Its slot is the new `SlotKey::Pair`, printed `.rows.cells[1][2]`. With it:
   - `render_key(rows.then(cells), it => (it.up.index, it.index), leaf)` is `renderIt` in nested loops.
   - `render_each(groups.then(items), item, filter=(s, k, _) => k.0 == s.selected)` is a `seqItem` collection.
   - `Signal::from(rows.then(cells), ...)` gets both keys.

   The keys are read when the view renders, so events keep JS's "route fixed at event time" (`rendered SeqItem collection stays frozen while sendAt captures producer commit`). The README's JS → MoonBit table mentions it.
4. **Fix (found by the assertion audit): `check_set` issues named only the component and view.** JS's lint gives the path to the reading site (`Prov.main > renderEach() > provided(nope)`). `check_set` reported `Reader.main` for every site, so two bad sites in one view were indistinguishable, and its "views:" list repeated a view name once per component (`views: main, main`). Its issues now carry the site path in `check`'s spelling (`Reader.main <div> > when_provided(lamp)`, `Pusher.main push_view(compact)`) and the views are listed once each. Tests: the two `check_set` tests in `jsport_check_set_wbtest.mbt` assert the exact issue texts.
